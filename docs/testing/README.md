# Update Testing Knowledge Map

这是更新平台与更新客户端测试的统一入口。

新会话不要一开始读取全部文档。先根据当前测试目标选择最小必要上下文。

## 1. 先判断你要做什么

| 目标 | 优先读取 |
|---|---|
| 第一次了解测试对象 | `overview/update-platform.md`、`overview/update-client.md`、`overview/update-lifecycle.md` |
| 执行某个已知测试流程 | 对应 `playbooks/*.md` |
| 测试过程中卡住 | `troubleshooting/README.md`，然后只读对应症状文档 |
| 查询稳定环境、路径或行为知识 | `knowledge/README.md` 及对应知识文档 |
| 记录第一次发现的新现象 | `LEARNINGS.md` |
| 查看整体覆盖面 | `TEST-MATRIX.md` |

## 2. 推荐加载顺序

```text
AGENTS.md
   ↓
本文件
   ↓
当前任务相关 overview / playbook
   ↓
开始执行
   ↓
失败时再加载 troubleshooting / knowledge
```

原则：**按需加载，而不是把整个仓库塞进上下文。**

## 3. 文档职责

### `overview/`

保存测试人员需要掌握的产品心智模型：系统由哪些部分组成、它们之间如何交互、正常更新生命周期是什么。

这里不是开发架构设计文档。只保存会直接帮助测试理解、定位阶段或选择验证点的信息。

### `playbooks/`

保存已经验证过、可以重复执行的测试流程。

每个 Playbook 应包含：目标、前置条件、入口、步骤/阶段、预期结果、证据、失败回退、停止条件。

### `troubleshooting/`

按**现象**组织排障知识，而不是优先按代码模块组织。

例如：检查更新卡住、下载不动、安装失败、UI 元素找不到、重启后状态异常。

### `knowledge/`

保存跨场景复用的稳定知识，例如日志入口、环境约束、已确认行为、术语。

### `LEARNINGS.md`

只保存尚未充分验证的新发现。它是暂存区，不是永久知识库。

### `TEST-MATRIX.md`

保存测试覆盖地图。它帮助 AI 判断“还有什么没测”，但不保存冗长执行日志。

## 4. 知识沉淀循环

```text
真实测试
   ↓
新发现
   ↓
LEARNINGS.md
   ↓
再次验证 / 证据确认
   ↓
┌──────────────┬──────────────────┬──────────────────┐
│ overview     │ playbooks        │ troubleshooting  │
│ 产品模型      │ 可重复测试流程      │ 症状与处理路径       │
└──────────────┴──────────────────┴──────────────────┘
              或 knowledge/
```

不要因为一次偶发现象就修改正式 Playbook。

## 5. 当前初始化状态

仓库目前只建立测试知识框架，产品具体事实应通过真实更新平台/客户端测试逐步补全。

禁止为了“让文档看起来完整”而猜测：

- 未验证命令；
- 未验证路径；
- UI 控件名称；
- 服务名称；
- 生命周期状态名；
- 平台与客户端之间的实际接口。

遇到未知信息时，允许探索一次；探索成功后应把可复用结果沉淀下来，避免未来会话重复探索。
